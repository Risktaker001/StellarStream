# Pull Request: Implement Clawback Module and Compliance Refactor

## Overview

This PR implements two features for the StellarStream Contract-V1:

1. **Clawback Module** — Allows a stream's sender to request the return of tokens that have already been withdrawn by the receiver. Opt-in at stream creation via `clawback_enabled = true`.
2. **Compliance Refactor** — Extracts OFAC/restricted-address logic into a dedicated `compliance.rs` module, migrates the restricted-address list to **persistent** storage, and adds event emission for every restriction change.

## Changes Made

### 1. Clawback Module

**New File:**
- `contracts/Contract-V1/src/clawback.rs`

**Files Modified:**
- `contracts/Contract-V1/src/lib.rs`
- `contracts/Contract-V1/src/types.rs`
- `contracts/Contract-V1/src/errors.rs`
- `contracts/Contract-V1/src/storage.rs`
- `contracts/Contract-V1/src/clawback_test.rs`
- `contracts/Contract-V1/src/topup_test.rs`
- `contracts/Contract-V1/src/vault_test.rs`
- `contracts/Contract-V1/src/test.rs`

**Implementation Details:**

**Lifecycle:**
```
sender calls request_clawback  →  Pending
  receiver OR governance calls approve_clawback  →  Approved
    anyone calls execute_clawback  →  Executed
```

**New Types (types.rs):**
- `ClawbackStatus` enum with 4 states:
  - `Pending` — request created, awaiting approvals
  - `Approved` — sufficient approvals received, ready for execution
  - `Executed` — tokens transferred back to sender
  - `Rejected` — expired or explicitly rejected
- `ClawbackRequest` struct with clawback_id, stream_id, amount, reason, approved_by_receiver, approvals, required_approvals, status, created_at, expires_at
- `ClawbackRequestedEvent`, `ClawbackApprovedEvent`, `ClawbackExecutedEvent` for event emission

**New Storage Keys (storage.rs):**
- `CLAWBACK` — prefix for clawback request records, keyed by clawback ID
- `CLAWBACK_COUNT` — counter for clawback IDs

**New Error Codes (errors.rs):**
- `ClawbackNotFound = 38`
- `ClawbackNotEnabled = 39`
- `ClawbackExceedsWithdrawn = 40`
- `ClawbackAlreadyExecuted = 41`
- `ClawbackInsufficientApprovals = 42`
- `ClawbackAlreadyApproved = 43`
- `ClawbackExpired = 44`
- `ClawbackRejected = 45`

**New Functions (lib.rs → clawback.rs):**
- `request_clawback` — sender creates a clawback request; validates clawback_enabled, amount ≤ withdrawn_amount
- `approve_clawback` — receiver or governance addresses approve; auto-advances to Approved when threshold met
- `execute_clawback` — anyone executes once Approved; transfers tokens receiver → sender (checks-effects-interactions)
- `get_clawback_request` — fetch a clawback by ID

**Key Design Decisions:**
- Clawback is **opt-in** — `clawback_enabled` must be set in `StreamOptions` at stream creation
- Amount constraint: `amount ≤ stream.withdrawn_amount` — cannot claw back unvested/future tokens
- `approved_by_receiver` always satisfies approval regardless of `required_approvals` value
- Governance multi-sig: any distinct non-sender address can count as a governance approver
- Expiry: requests with `expires_at != 0` that pass their deadline are atomically moved to `Rejected`
- `execute_clawback` does NOT modify `stream.withdrawn_amount` — it is a peer-to-peer transfer

**StreamOptions Updated:**
- `clawback_enabled: bool` field added to `StreamOptions`
- All existing tests that construct `StreamOptions` updated with `clawback_enabled: false`
- `create_stream` (non-options path) defaults to `clawback_enabled: false`

**Tests Added (clawback_test.rs):**
15 comprehensive tests covering:
- Basic request creation
- Receiver approval sets Approved status
- Governance approval path (multi-sig)
- Execute transfers tokens correctly
- Execute without approval fails (ClawbackInsufficientApprovals)
- Amount exceeding withdrawn_amount rejected
- Multiple clawbacks on same stream
- Partial clawback
- Expired request cannot be approved
- Expired approved request cannot be executed
- ClawbackNotEnabled stream rejected
- Double execute rejected
- Double approve rejected
- Non-sender cannot request clawback
- Get nonexistent clawback returns None

### 2. Compliance Refactor

**New File:**
- `contracts/Contract-V1/src/compliance.rs`

**Files Modified:**
- `contracts/Contract-V1/src/lib.rs`

**Implementation Details:**

The existing inline OFAC logic scattered across `lib.rs` has been extracted into a dedicated `compliance.rs` module with the following improvements:

**Storage Migration (Instance → Persistent):**
- `RESTRICTED_ADDRESSES` is now stored in **persistent storage** instead of instance storage
- Persistent storage survives contract upgrades and has no instance-TTL expiry, making it the correct choice for a compliance denylist that must outlive any individual stream or session

**New Public Functions (compliance.rs):**
- `restrict_address(env, admin, target)` — adds target to denylist; idempotent; requires SuperAdmin; emits `("complnc", "restrict")` event
- `unrestrict_address(env, admin, target)` — removes target from denylist; idempotent; requires SuperAdmin; emits `("complnc", "unrestct")` event
- `is_restricted(env, address)` — pure read; returns true if on list
- `require_not_restricted(env, address)` — panics with `AddressRestricted` if on list; used as a guard at entry points
- `load_restricted(env)` — loads the full list once; callers checking multiple addresses should reuse the returned Vec

**Enforcement Points in lib.rs:**
- **Stream creation** — both sender and receiver checked before any funds transfer
- **Withdraw** — receiver checked before any tokens are released
- **Proposal creation** — receiver checked before proposal is recorded
- **Receipt transfer** — new owner checked before receipt is moved
- **Batch stream creation** — sender checked once after batch validation

**Delegation Pattern:**
All five `restrict_address`, `unrestrict_address`, `is_address_restricted`, `get_restricted_addresses` entry points in `lib.rs` now delegate to `compliance::*` functions rather than containing inline logic.

**Tests Added (compliance_test.rs):**
16 integration tests covering:
- Restricted list starts empty
- Admin can restrict an address
- Admin can unrestrict an address
- Restrict multiple addresses
- Restrict same address is idempotent
- Unrestrict removes only the target
- Non-admin cannot restrict
- Non-admin cannot unrestrict
- `is_address_restricted` returns false for unknown address
- Unrestrict unknown address is a no-op
- Cannot create stream to restricted receiver
- Cannot create governance proposal to restricted receiver
- Cannot transfer receipt to restricted address
- Stream creation allowed after unrestriction
- Restricting one address does not block others
